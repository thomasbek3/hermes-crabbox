This is a bounded disposable qualification on **omarchy**, reached as thomas UID1000 over the previously authorized SSH endpoint. The driver verified exact Linux/amd64 image `sha256:5a03c9d2d1fc20683029c47683a3b0470ad2d7ce79eeb43ced1bdfba10770693` before creating any container. ## Permission layout and actual results

Controller UID27001/GID27002 owns directory0750 and socket0660. Root owns client.json0440 with GID27002. This directly exercises the transport's default trusted owner UID0 with distinct controller and client UIDs. Controller gets the socket directory writable; jobs receive only that directory read-only at `/run/cloud-role-broker`. Their roots and `/proof` source mount are also read-only. The controller DB lives in its private/tmp and is absent from job containers.

| Actual client | Result |
| --- | --- |
| UID27003/GID27002, role directory mounted read-only | Config read and UDS request/read succeeded; identical native-call retry returned identical pending record. |
| UID27004/GID27004, same directory mounted read-only | Config read and socket connect both denied with EACCES; client returns fixed configuration-unavailable error. |
| UID27003/GID27004 | Also denied. Matching the intended job UID without the permitted group is insufficient. |
| UID27004/GID27002, same directory deliberately mounted read-only | Created a distinct pending request with its own native call ID, by design: possession of this mount/group grants access to this attempt capability. UID alone is not identity authentication. |
| UID27003/GID27002, readable config owner27001/mode0440 | File open/read succeeds; default trusted-owner client policy rejects the non-root owner. |
| UID27003/GID27002, readable config owner0/mode0444 | File open/read succeeds; client policy rejects the broader mode. |
| UID27003/GID27002, role directory deliberately mounted rw | Broker works, but all tampering fails by Unix permissions (EPERM1/EACCES13), independently of EROFS. |
| UID27003/GID27002, role directory not mounted | Role directory and Docker socket absent. |

All three clients that could connect failed all tampering operations: writing/chmod/unlink of config, creating a file/directory in the mount, unlinking the socket and writing source. The receipt distinguishes EPERM1/EACCES13 from read-only-filesystem30. The intentional rw case isolates DAC enforcement; ordinary job cases retain readonly mounts. `/proc/self/mountinfo` and independent Docker inspect show the expected actual role/source mount modes, including the single deliberate rw role-mount experiment. This proves behavior for these Linux IDs/groups with the host's current namespace policy; it does not qualify every possible user-namespace remapping or future mount publisher.

The intentional same-group case is a boundary test, not a claim of cross-UID isolation: never expose an attempt's socket/config mount to another attempt merely because both jobs share a service group. Capabilities are stealable by code inside their authorized attempt. Broker scope/generation/expiry/role checks supply controller authority independently of filesystem UID. This run exercises real UDS/config permissions and fixed client behavior; prior source/dispatch fixtures cover payload conflict, cancellation, expiry and native identity delivery. No new real scheduler was introduced.

## Cgroup and runtime limits

All nine disposable containers used network none, all Linux capabilities dropped, no-new-privileges, read-only rootfs,128MiB memory with equal memory-swap limit,32 PIDs and0.25 CPU. The clients' and controller's Docker inspect receipts and in-container cgroup files show `memory.max=134217728`, `pids.max=32`, `cpu.max=25000 100000`. There was no Docker socket or controller DB in any job mount. No host networking or public ports were added.

Host `/proc/<pid>/cgroup` readback shows distinct **sibling** `system.slice/docker-<id>.scope` cgroups. Each container sees `0::/` through its cgroup namespace; this does not mean they share the same underlying host cgroup. This topology proves individual configured limits only. It does not enforce or prove an aggregate parent-attempt budget across controller, role seats, inference relay and provider service. Containers ran serially beside the controller; this is not a panel-concurrency, CPU throttling, OOM, fork-bomb or cgroup-parent admission test. Aggregate tree accounting and launch-time resource reservations remain separate integration gates.

## Ownership and cleanup

Every created container had exact labels `cwb.proof.owner=cloud-workbench-d4-permission-proof` and the unique run ID. Before stop/remove, the driver inspected full IDs, those labels and the exact image. All nine were removed; the exact-label inventory is empty. Runtime directory cleanup required the recorded private root-owned run path. Both uploaded/root-owned staging directories were separately removed only after verifying ownership and the expected manifest digest. `scripts/cleanup-d4-linux-staging.py` performed removal and `evidence/d4-linux-corrected-staging-cleanup.json` records actual UID/mode/device/inode/manifest digest, exact command, timestamps and post-removal checks for both paths. Existing images, services, directories and other runs were not cleaned up.

Remaining gates: actual production service/mount publisher wiring and account/group policy; real Store parent lifecycle and atomic child/provider reservations; native transcript replay across restart and provider call-ID uniqueness; separate broker/private-controller channel; aggregate resource accounting. This closes the scoped actual-Linux permission experiment, not all of D4/H2 or a deployment acceptance gate.

The corrected driver hashes its executing file against the frozen manifest. Every process records the imported module paths/hashes under /proof/source and Python3.13.15. Pending capability publication uses fsync plus atomic rename; root opens it with O_NOFOLLOW and checks the open regular file descriptor and bounds. Controller shutdown records Docker exit0, final stopped health, zero connection attempts, three distinct pending rows and absence of its socket before removal. `scripts/verify-d4-linux-receipt.py` independently validates these receipts and every snapshot/source hash; it makes no remote mutations.
