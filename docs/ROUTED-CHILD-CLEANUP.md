# Combined routed child cleanup

`RoutedChildCleanup` consumes trusted scheduler/runtime/spec objects, the exact `QuiescedStage`, and every `WorkerService` owning an execution grant for that child. It does not accept model-provided cleanup assertions. `collect()` produces a durable, bounded, hash-addressed receipt in the controller runtime directory while keeping the scheduler seat and all root account reservations held.

The collector verifies the durable fenced launch, generation, current root ownership, caller spec and frozen profile. Every child grant must be revoked and covered by one exact supervised service. Request leases and dispatch rows must have identical membership; a missing dispatch is an unresolved effect, not an empty successful run. Limits are 32 grants/services and 1024 request rows; exceeding them requires reconciliation.

Service shutdown fences admission, signals cancellation, joins the synchronous handler and closes the listener and journal. A timed-out callback retains its handle and journal. Executor quiescence separately closes direct admission and requires all observed supervisors to have stopped. An earlier failed supervisor remains a sticky failure. Neither thread shutdown nor socket removal proves provider container cleanup.

Under the root's account locks, the collector checks current authority again and rechecks exact caller removal through the runtime journal. It reconciles uncertain provider operations only with the existing definitive operation protocol, never from an empty resource listing. It invokes dispatch cleanup for every exact request, including already cleaned/delivered rows, so pending credential snapshot cleanup is retried. It then requires released request leases and immutable physical cleanup receipts matching request, grant, reservation, attempt, generation, profile and runtime resource identities. Membership and root/account ownership are checked again before saving evidence.

The evidence contains identities and receipt hashes, never provider responses or credential values. A failed or partial collection produces no successful aggregate receipt. Complete bytes are fsynced to a random private file, then atomically published without replacing an existing final receipt. Linux uses renameat2/RENAME_NOREPLACE; macOS uses renamex_np/RENAME_EXCL. Interrupted temporary writes can be retried; corrupted existing final evidence remains refused and preserved. Previous completed physical removals remain durable and retries rerun only pending material work. An explicit runtime material-cleanup hook is required. Root account reservations remain held across stages; neither `cleanup_owner` nor previous-owner takeover is used to release a child.

After the controller has independently committed the protected outcome and moved the child to a terminal state, `scheduler.release_child(..., verifier=cleanup.verifier)` performs fresh combined verification and the existing generation/version compare-and-swap. The cleanup collector itself does not mark the child terminal, pass a verification gate, export a produced revision or advance the workflow. A failed child can release its seat after exact cleanup without being marked successful.

The tests compose a real scheduler, SQLite leases, runtime reader, UDS service and supervisor wrapper with synthetic Docker/provider adapters. They cover exact cleanup, terminal child release, retained account authority, multiple requests and grants/services, concurrent release, pending private material retry without duplicate removal, uncertain operation refusal and definitive recovery without restart, missing/foreign grant membership, early stale-target refusal, bad receipts, interrupted publication and failed supervisors. Actual provider authentication and deployment remain separate acceptance gates.
