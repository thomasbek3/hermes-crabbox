# Routed root delivery evidence policy

`routed_delivery_policy.collect_root_delivery_proof(scheduler, root_id, *, expected_generation, selected_revision, forbidden_values=())` reads one qualified, versioned, complete frozen workflow. It returns a frozen `RootDeliveryProof`; it does not create an intent, stop a runtime, release an account, change a root outcome, or promote a session workspace.

The collector first takes a bounded scoped SQLite snapshot (8,192 rows / 16 MiB) in the existing short control transaction. It then uses a detached in-memory database for the real historical stage/task decision and release readers. Filesystem validation happens outside the live transaction. Before returning it compares immutable evidence again in a fresh control transaction. Full original-root and selected revision trees are rehashed; the protected tested revision is rehashed for workspace delivery. Known forbidden bytes are checked in their retained contents and manifest strings, as well as decision/public evidence.

The exact current catalog is required, with one completed child/request/seat per stage, a pass gate and authenticated release for each stage, and no extra child/request. Every linked broker call must match an admitted request; unlinked nonterminal broker calls block delivery. Prior context refs must be the complete ordered list of earlier decision artifacts, in both the frozen launch assignment and broker request. Each decision's input binding must equal the actual carried revision binding. Only coding stages change the carried revision. Protected acceptance must be final, verified, nonempty, tied to the exact qualified environment/check definitions and requested mandatory criteria, and tested against contents identical to the selected revision.

A workflow containing protected acceptance produces `kind=workspace`, `outcome=verified`, with a selected revision/artifact. Standalone planning, code review, investigation, and other supported readonly catalog workflows produce `kind=report`, `outcome=unverified`: `selected_revision_sha256`, `selected_artifact_id`, and `final_task_decision` are null; the original carried revision stays pinned. They do not silently acquire a protected step. The parent delivery transaction must increment its delivery version / last artifact while preserving the existing workspace pair for report delivery.

## Serialization and final transaction

`proof.canonical_json`, `proof.sha256`, `proof.to_dict()`, and `RootDeliveryProof.from_json(raw)` provide the durable private record. Canonical JSON uses sorted keys, compact separators, UTF-8 (`ensure_ascii=False`), and rejects nonfinite values and duplicate keys. Decoding bounds the document to 256 KiB and validates exact keys, identifier/digest/integer types, catalog stage order, chain/selection consistency, and absolute private paths. This is structural validation, not cryptographic signature authority.

`proof.public_record()` is the safe downloadable projection. It contains kind/outcome, root/session/owner/project/turn/generation, workflow/environment hashes, input/carried/selected hashes, ordered `decision_refs`, report artifact references and final task reference. It contains no database rows, private paths, scripts, or credentials. Each decision reference has `step_id`, `role`, `child_id`, `generation`, `artifact_id`, `sha256`, `input_revision_sha256`, `carried_revision_sha256`, and the authenticated release payload's `release_sha256`.

The full private record additionally retains the database path, a scoped immutable-evidence snapshot hash, and selected/carried revision path/hash/binding for trusted crash recovery. It must not be published as the delivery artifact.

`validate_db(db, proof)` requires an existing transaction. It performs database-only snapshot comparison and binds the public projection back to actual root scope/frozen digests, root-input metadata, decision metadata, release receipt hashes and the selected revision locator. It performs no filesystem reads or runtime callbacks. Root running/verifying/completed lifecycle, root cleanup state/version/cancellation, session delivery fields and provider cleanup state are excluded from evidence comparison. Consequently it explicitly does **not** grant current authority: the orchestrator must separately validate cancellation, controller/account ownership, physical cleanup, root generation, intent envelope, expected delivery version/base CAS and terminal transition in its final transaction.

Controller-private retained files are trusted to remain immutable between collection and commit. `validate_db` does not detect subsequent same-path file tampering. A crash recovery path requiring renewed file availability must recollect/validate files outside the short transaction before final commit. Historical readers remain responsible for exact finalization evidence, and their independent correction tests are not replaced by this module.

## Local evidence boundary

`tests/test_routed_delivery_policy.py` composes the real qualified six-stage feature controller chain, plus exact planning and code-review report workflows. Provider inference and Docker are synthetic; local collector/script subprocesses and Unix service lifecycle are real fixture components. Tests cover missing/changed chain evidence, rejected/incomplete work, root-file drift, stronger secret policy, strict durable schema, database-only validation and permissible root lifecycle changes. Adversarial snapshot/reader mutations are negative tests, not evidence that an untrusted worker can alter controller rows. No remote execution, production delivery, actual model inference or provider qualification is claimed by these tests.

Latest focused result: **52 policy tests passed in 5.17s** (`evidence/routed-delivery-policy-frozen-tests.xml`). A preceding broader run passed 106 cases; its final 107-case repetition preserved one 50 ms existing cleanup-read deadline failure (`test_routed_decision::test_atomic_pass_replay_and_exact_release`, before delivery-policy invocation), with 106 passed. No production deadline was changed or failed action retried. Both receipts remain in the binding; the focused result is not a claim that the broader failure passed.
