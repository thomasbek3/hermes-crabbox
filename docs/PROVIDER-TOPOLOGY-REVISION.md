# Proposed D9: response relay and disposable provider requests

Status: reviewed design correction; Fable REVISE independently dispositioned below. Not implemented or deployed yet. Scope is a concrete correction to D1 lifecycle, not reduced provider isolation or a release exception.

## Problem

InferenceTransport deliberately reports only process-group cleanup. The Linux proof demonstrated an escaped child surviving group termination. Releasing credentials therefore requires an outer container cleanup/fence. If the HTTP listener shares that disposable credential-bearing container, terminating it also destroys the pending response path. Keeping it alive solely to return a response leaves cleanup unproven.

## Proposed topology

Hermes uses its qualified native chat-completions SDK against a per-attempt loopback HTTP relay inside the Hermes container. That relay translates HTTP into a bounded request over an attempt-scoped Unix socket mounted from the existing trusted worker. It holds only an attempt-scoped inference capability, never provider credentials, Docker access or the control-plane API token. Its process/resources count inside the caller's existing execution envelope. No host network exposure or new published port is needed. The native Hermes runtime/tool loop remains unchanged; the relay cannot execute model-requested tools.

The trusted worker owns a single ProviderLeases facade and authenticated UDS dispatcher. API processes may submit/cancel through Store but do not instantiate an independent provider owner. The worker validates the hashed capability, current attempt/generation/cancel fence and frozen profile; it acquires an exclusive request/refresh lease and binds a prepared, immutable provider container ID before starting it. A pending/create/start/collect/cleanup record is durable so restarts cannot launch a duplicate or treat an absent-not-yet-started container as cleaned. Runtime creation is serialized with revocation and cleanup; a stale dispatch cannot start later after cleanup receipt.

Only the short-lived provider container mounts the one persistent, dedicated auth capsule, and only while its account reservation/request lease is exclusive. It has no workspace, tools, Docker socket, control token or arbitrary egress. It runs the pinned unmodified CLI with tools disabled. Provider token provisioning occurs inside this container through the supported dedicated setup-token path; no fabricated credentials.json, personal login borrowing, or token bytes in relay memory/argv/logs. Existing host canonical storage remains private and is mounted by path; the worker need not read its contents for the new route.

The provider emits bounded structured output into trusted collection. The worker saves the candidate response durably, stops/removes the exact request container and its owned gateway, proves cleanup including no pending starts, then releases the request lease and sends the retained response back over UDS. If cleanup is uncertain, it quarantines ownership and returns a fixed failure; it does not return a successful response that implies credentials are reusable. Process-group success alone never releases a lease. Parent cancellation discards success and fences dispatch before cleanup.

Account reservation remains held by a logical persistent owner across multiple requests and child waits, preventing legacy jobs from taking the same auth identity between requests. There is no idle credential-bearing process. A new request container can mount the same persistent capsule only after the previous mount/process is terminated or equivalently fenced. Request container ID must be separate from persistent owner identity; do not fabricate a64hex value and call it a container ID. Current reservation API requires revision to represent logical owner and per-request runtime ID explicitly. A worker restart quarantines/reconciles the old owner and requests before acquiring a new owner epoch; never adopts uncertain refresh state automatically.

## Accounting and boundaries

The loopback relay runs within the caller envelope. Provider container plus provider gateway use the existing active-caller provider allocation (0.5CPU/1GiB/128PID total), with explicit sublimits summing within it. Trusted worker dispatch/collection are bounded within existing controller reserve: finite pending queue, body/output caps, worker thread/process caps and root admission already required by D2. No persistent additional model slot, unbounded callback thread or hidden third execution slot.

This applies to new routed Hermes only. Historical direct-Claude jobs and canonical credentials remain unchanged. Updated Store admission and legacy SQL triggers prevent account collisions once an account reservation exists. Older workers must be stopped/upgraded before activation; triggers fail closed but do not make old workers gracefully compatible.

## Required acceptance before real activation

1. Actual pinned Hermes CLI performs a file-tool loop through loopback HTTP/UDS dispatch/codec with a synthetic CLI; preserves tool IDs/results and disables or inventories auxiliary inference calls.
2. Durable request state proves create/start/revoke/cleanup interleavings, lost responses and worker death without duplicate CLI invocation; bounded reconciliation must inspect actual container/gateway identity.
3. Two serial request containers use one logical auth owner; no simultaneous mounts or refresh writers, including cancel/restart/lease expiry. Logical owner and request runtime identities are typed separately.
4. Real supported setup-token CLI request proves exact flags/schema/model/effort under existing account authorization; no new API spending or alternative model substitution.
5. Omarchy proof binds source/image/config/process/cleanup evidence. Existing jobs remain retrievable and unaffected.

No activation, token access or new provider call is authorized by this proposal itself; existing task authority still governs implementation. D1/D2 wording changes and implementation follow independent review disposition.

## Concrete decisions after Fable REVISE

This section resolves the design omissions identified by the checkpoint review. It supersedes ambiguous prose above; runtime proof remains required.

### Identities and durable tables

`Reservation` binds account_id, persistent_owner_id (logical, not a process), reservation_id, owner_epoch and controller_instance_id. Remove owner runtime_id from the new topology; never invent a container hash. `RequestLease` binds reservation, request_id, grant_id, purpose, expiry plus a durable `provider_dispatch` record. Dispatch records contain immutable attempt/generation/profile_digest, request_nonce, payload_digest, launch_nonce, provider_container_id and gateway_container_id (nullable only before successful create), deterministic resource names, bounded response digest/path, state, cancellation flag and failure code. Unique(attempt_id,generation,request_nonce) prevents duplicate inference; same key/different payload or profile returns409.

States: admitted → create_intent → created → start_intent → running → collected → cleaning → cleaned → delivered. Terminal failed/quarantined remain durable; response collection cannot make a request successful until cleaned. Each transition uses generation/state CAS. An unknown create/start result is quarantined, not interpreted as absent/stopped. Existing unreleased experimental reservation rows cannot be silently adopted under the revised schema: explicit compatibility detection/refusal or reviewed migration is required.

Request cleanup target includes immutable reservation/epoch/request/launch nonce plus exact bound provider/gateway IDs and dispatch state/version. Owner cleanup covers all outstanding dispatches and the worker's exclusive owner lock. Resource labels: io.cloudworkbench.provider-reservation, provider-epoch, provider-request, provider-launch, provider-component. Components are exactly provider or gateway. Labels are applied in docker create and independently verified against the returned full ID before bind/start/remove. Names include reservation epoch and launch nonce; reconciliation searches only exact labels/names.

### Start, cancellation and unknown Docker outcomes

One OS advisory flock per account in a controller-private directory serializes dispatch/start and cleanup across threads and worker processes. The new worker first acquires the account lock, then quarantines/reconciles the previous controller epoch. A worker process death releases the OS lock but not durable ownership. No model/container can access the lock directory. SQLite transactions stay short and never span Docker calls.

Under that lock: validate live grant; persist create_intent/launch nonce/names; create stopped gateway/provider with bounded Docker calls; verify labels and bind full IDs durably; recheck cancellation/grant; persist start_intent; start; persist running. No alternate start path may bypass the lock and durable state. API cancellation atomically fences the attempt/grants; worker observer polls that fence at most every250ms and on UDS disconnect. If cancellation races the final authorization/start boundary, cleanup waits for the same lock and terminates the started process; it never releases ownership based on pre-start absence. After running, request execution need not hold the dispatch lock; every stop/remove/cleanup path reacquires it.

An interrupted or timed-out Docker create/start is an unknown external effect. Killing the Docker client does not prove the daemon stopped processing. Mark dispatch quarantined and retain ownership; absence on one inspection is insufficient to release it. Reconcile exact labels plus recorded operation outcome; if definitive outcome cannot be obtained, require operator-assisted daemon/resource reconciliation. Do not stop the shared Docker daemon automatically. All normal successful create/start paths have exact IDs; crash-after-create-before-bind is recovered by exact immutable labels under the account lock.

### Delivery identity, retries and clocks

Each accepted HTTP inference receives one cryptographically random request_nonce, journaled by the per-attempt relay before UDS transmission. The worker persists the key/payload/profile binding before provider work. UDS reconnect/retry retains that nonce: it waits for the existing dispatch or returns its cached bounded response, never launches another provider. A genuinely new identical prompt gets a new nonce; payload hashing does not conflate it with an earlier request.

Configure SDK max_retries0, Hermes api_max_retries1 and HERMES_STREAM_RETRIES=0. Actual pinned-source qualification found an additional unconditional primary-transport recovery path, so these settings do not intrinsically disable all retries. The controller must enforce the interruption below; configuration alone is not the gate. Relay does not half-close its HTTP or UDS write side while awaiting a response. If the outer HTTP response is lost, do not transparently regenerate: interrupt the attempt with response_delivery_unknown, retain cached response for controller inspection and use the explicitly reconstructed follow-up contract. Native resume/replay of that response is not claimed. A test must prove the real CLI emits only one HTTP request in the lost-response case under the actual controller interruption path. Synthetic native process-group interruption passed with one HTTP/UDS/provider execution; production distinct-UID/container interruption remains an activation gate. If interruption cannot prevent another HTTP attempt, activation stays blocked until the controller boundary is corrected or stable nonce propagation is implemented at the native boundary. The relay fences subsequent traffic regardless; it never treats a new native retry as permission to execute another provider request.

Initial bounded budgets: provider execution120s, stop grace10s, forced stop/inspect/remove aggregate20s, collection5s, admission5s =160s. Worker/relay response deadline180s; local HTTP execution deadline190s; native SDK timeout210s. All are clamped to remaining root/attempt budget; never begin if required cleanup reserve is unavailable. Docker command failures/timeouts quarantine rather than extend those budgets indefinitely or declare cleanup. Actual measured normal/failure cleanup must fit before activation. Queued account ownership waits happen before compute admission and are separately visible, not charged as invisible running inference.

### Credentials and resource arithmetic

The existing dedicated setup-token is already generated. Do NOT run interactive setup-token per request. Mount the canonical file read-only at /run/secrets/claude-token. A trusted bootstrap INSIDE the provider container validates/reads that file and supplies CLAUDE_CODE_OAUTH_TOKEN only to the pinned CLI child environment; it must not appear in argv, logs, persisted response or controller/relay memory. HOME/config are private tmpfs. No auth-home fabrication or credential copyback. This token mode is non-refreshing in our implementation: refresh purpose is disabled for this registered profile. A future refreshable provider retains separate qualified refresh machinery, but it is not used or claimed for this token. CLI auth rejection quarantines the account until authorized reauthentication.

Per active2CPU/4096MiB/512PID caller envelope: Hermes+loopback relay1.4CPU/3008MiB/352PID; caller gateway0.1CPU/64MiB/32PID; provider0.4CPU/960MiB/112PID; provider gateway0.1CPU/64MiB/16PID. Sum exactly2CPU/4096MiB/512PID. Provider+gateway total equals the D2 allocation0.5CPU/1024MiB/128PID. Apply explicit per-container limits; do not leave Hermes at the old full envelope and add sidecars. Qualified peak health, PID sufficiency and actual Docker HostConfig sums remain required; static arithmetic is not operational proof. Idle or waiting requests do not create provider/gateway containers.

`legacy_account_busy` and `provider_account_reserved` are durable queue reasons evaluated before routed root compute admission. Reserve the root's needed qualified accounts in stable account-ID order or roll back all new reservations before occupying slots; no hold-and-wait across accounts. One root still owns coordinator+child envelopes; panels serialize as D2 specifies. Initial inference caps:32 new requests per attempt and128 per root,60 requests/minute per attempt (burst4), capped by the root wall budget. Retries with the same nonce do not consume another call; new nonce does. Cap refusal is visible and never resets on a new capability or worker restart. These defaults are explicit configurable policy, frozen per root, not backend token/spend authority.

### Relay UID and journal isolation clarification

A0700 journal owned by the Hermes/tool UID is not trusted against tool execution. The production relay must run as a distinct dedicated non-root cloud-relay UID, started by the trusted worker with Docker exec --user inside the caller cgroup. The container retains dropped capabilities and no-new-privileges; do not add SETUID or SYS_PTRACE to make this work. Relay code is baked/root-owned/read-only. A controller-provisioned per-attempt persistent journal mount is0700 owned by relayUID, DB0600, never exported as a task artifact. Hermes/tool UID cannot modify/read that journal, signal/ptrace the relay or alter its code. The capability remains scoped to the attempt; separate UID does not broaden authorization. Docker control remains exclusively with the worker.

Actual isolated two-UID proof must verify journal access denial, signal/proc-environment denial, source immutability, same-cgroup accounting and lifecycle cleanup before activation. Host UID allocation/provisioning is a deployment step requiring real host verification; no numeric UID is assumed available. Synthetic same-UID tests prove protocol mechanics only. Relay restart uses its own existing durable journal; a lost or inaccessible journal interrupts the attempt rather than regenerating nonces and re-executing uncertain requests.
