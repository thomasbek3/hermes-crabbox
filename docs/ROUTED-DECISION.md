# Routed task-acceptance decision checkpoint

This local controller module supports only the frozen `acceptance_verification` role at step `verify`. It does not implement planning/review contracts, workflow remediation, next-child admission, root completion or final session promotion. No schema changes or live deployment accompany it.

`complete_task_verification(scheduler, routed, caller, results, prepared, verifier, *, input_revision, services, forbidden_values)` first recognizes an exact historical decision, otherwise invokes the load-only protected-verification reader. It never executes missing checks or repairs missing publication. It reloads the saved worker observation under current authority and requires completed execution, exit zero and no failure, then compares that observation to its published artifact. In-memory success flags cannot substitute for this read.

The assigned input revision and readonly captured candidate must have identical verified files, directories, selection and scope. Their different binding-dependent manifest hashes are preserved. The tested subject is the candidate; the carried output remains the original assigned input. Protected task acceptance is explicitly separate from semantic model judgment.

The private canonical decision file is staged before one bounded SQLite transaction. Current root/child, generation, controller/account owner, client, cancellation, deadline/budget, assignment, acceptance, artifact rows, protected receipt event and cleanup membership are rechecked. The transaction commits the decision artifact, terminal result, lifecycle events, grant revocation and passing/rejected gate together. `needs_review` commits no gate. A file left by a failed transaction is not a decision. Exact terminal replay validates canonical file/hash, referenced metadata, launch/assignment identity, lifecycle/artifact/decision/gate events and terminal result without granting fresh authority or calling a runtime.

`release_decided_child(..., input_revision=..., decision_sha256=..., services=..., forbidden_values=...)` reconciles each exact verifier and caller/provider cleanup outside SQLite. It compares verifier runtime identities with the decision's observed check identities, then rechecks membership/current owner/generation and CAS-clears occupancy together with a full hashed release receipt event. Unknown cleanup retains occupancy. Cancellation does not forbid cleanup. Exact release replay is a historical read and never touches a later account owner or invokes cleanup callbacks. Root account reservations remain held. The old `RoleScheduler.release_child` refuses decision-managed children before invoking its callback, preserving its prior behavior for other children.

Existing controller APIs `RoleScheduler.transition` and `record_step_gate` can still construct older manually authorized outcomes. Restricting production orchestration to the protected composition remains an explicit activation requirement; this module does not claim to remove all alternate controller APIs. Controller ownership takeover and missing legacy hash-only release events are not silently adopted. Terminal needs-review/reject remediation requires an explicit fresh attempt policy.

Tests use real Store/scheduler/budget/worker cleanup and saved observation/candidate composition with synthetic Docker/check observations. They are not live provider or Linux decision-execution proof. An initial failed-observation regression used an invalid synthetic failure enum, preventing snapshot creation; correcting it to the accepted `hermes_execution_failed` enum exercises a genuine saved failed observation, including a forged successful in-memory copy.

## Historical evidence integrity correction

`load_finalized_task` and exact decision/release replay share the strict `_record` path. The historical body has an exact schema (with the three stage-contract fields present only for qualified roots), canonical duplicate-free JSON, typed generations/versions/digests/account identities, and the original input producer binding. That producer may be the root or a prior coding child; it is not rewritten to the verifier child.

Historical reads now require the saved candidate manifest, protected-verification receipt, and worker-observation artifact bytes to remain available, regular/single-link, bounded and hash-identical to their committed metadata. Their artifact and publication events are checked. The worker result and event stream are reparsed through the existing pure collection parser; the qualified final answer must still match the frozen contract/output digest. Protected receipt record order/count, runtime IDs, cleanup flags, mandatory criteria and outcome are checked against the saved plan. This authenticates recorded evidence; it does not rerun Docker checks, consult a new account owner, or grant current execution authority. Missing/corrupt retained evidence fails closed. Evidence retention must preserve these dependencies while historical delivery/context authentication is required.

The generic task-context branch now invokes this same authenticated historical loader before projecting either the task decision or its linked worker summary. Nonacceptance stage context still uses its separate finalized-stage reader. Context content remains untrusted data. Unit context fixtures explicitly stub finalizer authentication when testing independent scope/path/render rules; a separate real controller fixture completes/releases a task and then projects its decision and observation into a subsequent generic stage. This is local synthetic-runtime evidence, not a production six-stage run.

Verification:99 decision/context tests and65 qualified-acceptance/delivery-policy integration tests passed. The first expanded run's10 failures were fixture setup errors: attempted mutation of an immutable gate and unlink under a readonly candidate directory. The corrected corruption fixtures retain the SQL gate guard and make only the disposable test directory writable. No production guards or transaction deadlines changed.
