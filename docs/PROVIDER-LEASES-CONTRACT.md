# Controller account reservation contract

This module adds account ownership and request/refresh exclusion to the controller's existing SQLite database. It does not activate a provider service, launch containers, provision credentials or implement bearer authentication. `ProviderLeases` requires a trusted cleanup verifier and inspector identity at construction. All IDs are internal database references, never permission to call a public API.

## Ownership and admission

A controller explicitly registers an immutable `account_id -> (legacy_agent, persistent_owner_id)` binding. Both legacy-agent and persistent-owner aliases are unique. The binding cannot change even when idle. Registration creates no lease and changes no old attempts.

`reserve(account_id, persistent_owner_id=...)` runs in the same `Store._tx()` / SQLite BEGIN IMMEDIATE transaction as historical job admission. It checks for any live attempt using that account's legacy agent. `Store.claim_next()` checks the active provider reservation before moving a matching queued attempt to preparing; a blocked attempt records `provider_account_reserved`. Direct Store transitions from a nonlive state into live are also fenced. Narrow SQLite INSERT/UPDATE triggers reject a matching live legacy state while an account reservation exists, including raw old-writer SQL. Thus a concurrent legacy claim and provider reserve cannot both succeed through these controller paths. Existing one_live_credential and all other legacy indexes remain intact.

The reservation binds a monotonically increasing account epoch, random reservation ID, controller instance and persistent logical auth-owner identity. Reserve must precede runtime start or mounting/using the credential. The separate D9 dispatcher persists a launch intent, verifies the actual four resource identities and binds them before start. A live reservation is retained until exact cleanup proof, including when no inference request is active. A competing old direct-Claude job cannot reuse that identity while the new provider owns it.

A fresh `ProviderLeases` controller instance cannot issue grants/requests or authorize old requests belonging to another instance. The old reservation remains held and visible with `requires_reconciliation`; it is not reclaimed by timeout. Recovery must prove full old-owner cleanup and acquire a new reservation/epoch. Construct this facade once for the owning controller, not once per HTTP call. Service failure under the same controller calls `quarantine(reservation)` to revoke all grants and retain ownership pending reconciliation. The module does not detect a process crash itself.

## Two levels of permission

`issue_grant(reservation, attempt_id=..., generation=..., ttl_seconds=...)` is a trusted controller decision for a currently live, uncancelled attempt with an unrevoked owner. It is distinct from `acquire_request(reservation, grant_id, purpose='inference'|'refresh', ttl_seconds=...)`. No model text can select another account or generate an execution grant through an exposed listener: there is no listener in this module. Future provider-service bearer capabilities require separate authenticated, hashed-token issuance; these opaque IDs must not be repurposed as bearer credentials.

Only one request or refresh can be held/cleaning/quarantined per owner. The request lifetime is clamped to the grant lifetime. Expiry denies new use but never releases an active request or owner. Observed grant expiry/revocation persists; a subsequent clock rollback cannot revive that observed expired grant. Observed request expiry quarantines the request. `authorize_request(lease)` rechecks owner instance, exact identity, grant expiry/revocation, attempt generation/cancel/state and owner revocation. Admission and authorization are not permission for future calls after state changes: the eventual service must use the gate at the request boundary and cancel active processes when revoked.

Store cancellation, generation fencing and terminal transitions revoke execution grants in their existing database transaction. A running request becomes quarantined and retains account ownership. `revoke_grant` and `quarantine` similarly deny new access without implying the process stopped. A waiting Hermes coordinator releases its cleaned request lease before waiting on children; it may retain its execution grant. Refresh uses the same exclusive request slot. No retry, prompt replay or duplicate request is performed automatically after a crash or lost response.

## Trusted cleanup proof

`cleanup_request(lease)` and `cleanup_owner(reservation)` first durably freeze the exact identity with a fresh cleanup nonce. The mandatory verifier then runs outside the SQLite lock. It receives a typed `CleanupTarget` including scope, reservation/epoch/controller, request/grant/attempt/generation when present, immutable per-request container/network bindings, frozen timestamp and nonce. It must independently inspect the actual resources and return a typed `CleanupReceipt` matching that target, trusted inspector ID, timestamp and SHA256 evidence reference. Boolean, string, model-provided dictionary, stale identity, old nonce and wrong-inspector receipts fail closed. No data model or SHA hash alone makes an inspection truthful: the trusted callback and eventual live inspector are the authority boundary.

`terminated` must prove the owned process/resource scope has stopped. `fenced` must prove it can no longer use or mutate the credential/auth state or conflict with reassigned ownership; a network-only fence or a model claim is insufficient. Request proof must cover all subprocesses for that request. The real service verifier must also quiesce/fence pending or concurrently starting dispatch before treating absence as cleanup; an earlier authorize_request result cannot authorize a delayed launch after revocation. Database admission alone does not make a process start atomic. Owner proof must cover the persistent service and all outstanding requests/refresh writers. Process-group-only results from inference_transport are explicitly insufficient for owner release.

After verification a second database transaction rechecks the same reservation/epoch, cleaning state and nonce before release, then stores the receipt. Failed callback, controller crash or changed identity leaves the reservation/request held, cleaning or quarantined. Retry uses a fresh cleanup nonce, so an old receipt at an identical clock timestamp cannot authorize a later cleanup. Releasing one request does not release the account owner; releasing the owner revokes all grants and releases outstanding requests only under the wider owner proof.

## Compatibility and proof boundary

Schema changes are additive provider_* tables/indexes and two narrowly scoped attempt INSERT/UPDATE guards. Existing attempt data, schema_version1, history and indexes are not rewritten. No account registration is automatic; existing claim behavior is unchanged when no account is reserved. Tests exercise old-database reopening, legacy claim/reserve races both directions, cancellation/restart/expiry, stale identity receipts, callback lock separation and rechecking. Actual service upgrades still require the normal idle/backed-up deployment procedure. An older controller binary cannot queue gracefully under a reservation: its conflicting SQL raises provider_account_reserved instead of silently bypassing ownership. Stop/upgrade older workers before provider activation; the triggers are a rollback safety fence, not an older-worker compatibility promise.

No live deployment or actual cleanup inspector is provided. Remaining integration gates: D2 capacity/root reservation, trusted runtime construction/start ordering, sole persistent credential store, real request dispatch/cancellation/reconciliation and authenticated service grants. Synthetic typed receipts in tests validate transaction behavior only; they are not physical cleanup evidence. Released records are retained for audit; pruning/retention is not implemented here.

## Review disposition and composition gates

The owning **worker dispatcher**, once implemented, must construct the single facade and perform reserve, grant, request authorization and cleanup calls. The API process must forward authenticated control intent to that owner rather than construct a second facade to authorize inference. No service startup integrates this module yet, so that composition assertion and its readiness check remain a pre-activation gate. A worker restart intentionally requires physical old-owner reconciliation; persisting a shared instance ID to bypass that check is not the default recovery policy.

`active_request(reservation)` reconstructs a durable held/cleaning/quarantined request for trusted recovery when its Python object was lost. It does not authorize inference, remove expiry/cancellation or bypass a changed controller instance. Same-instance request cleanup can use that reconstruction; a restarted owner still requires the wider owner cleanup before reassignment.

The reservation is a logical persistent account owner. Per-request provider and gateway containers are separate from the attempt runtime containing Hermes and its tools. They must be separate under D1; requiring equality or requiring the `hermes` attempt agent to equal legacy `claude` would break that boundary. Issuing a grant is itself a trusted controller policy action. This foundation does not infer or qualify which provider profile/account a role may use; the eventual immutable profile router must select that binding before grant issuance. D9 now separates those identities explicitly; see `PROVIDER-DISPATCH-CONTRACT.md`. The earlier lease review/evidence remains bound to its historical source, not the revised dispatch implementation.

Current retention does not delete attempt/session/client rows. The new foreign keys intentionally retain audit references; future physical history deletion needs a separately qualified ledger-retention/migration plan and must not cascade away held ownership. Fable returned REVISE; independently corrected findings and accepted integration gates are recorded in `evidence/provider-leases-review-disposition.md`. No PASS re-review was performed.


D9 compatibility update: the local experimental provider schema is version 2. Existing pre-D9 provider tables, partial schemas and incompatible version-2 dispatch layouts are refused without rewriting rows. Ordinary controller databases without provider tables still receive additive tables. No live schema upgrade has been run. `cleanup_request` and `cleanup_owner` hold the same private account flock used by dispatch, including while the trusted callback runs outside SQLite. Unknown pending create/start/cleanup operations prohibit cleanup until definitive, identity-bound operation reconciliation. The OS lock disappears on process death; the durable reservation does not.
