# Owned worker socket service lifecycle

`WorkerService(server: WorkerSocketServer, *, poll_seconds=.05)` takes exclusive ownership of a newly constructed, unstarted synchronous Unix socket server and its exact `WorkerDispatcher`. Do not run `serve_forever`, manipulate `server.dispatcher`, or close the original dispatcher/journal from another owner after constructing this wrapper. A server already managed by the wrapper is refused. The constructor cannot detect an unrelated caller already serving a raw server; unstarted exclusive handoff is a trusted controller prerequisite.

`start()` launches one retained **non-daemon** `service_thread`. It runs the existing synchronous `handle_request` with a bounded idle poll rather than `serve_forever`. It never invokes `BaseServer.shutdown`, which can wait forever when `serve_forever` is unstarted or gone. No thread is forcibly terminated or abandoned to pretend cleanup succeeded.

`stop(timeout_seconds=5)` permanently fences new dispatches, signals each admitted dispatch's existing cancellation event, waits for the current synchronous socket handler to drain, and closes the listening socket with the existing inode-guarded `server_close`. It leaves the dispatcher journal open for inspection. `close(timeout_seconds=5)` performs that stop and additionally closes the dispatcher/journal only once no handler or callback can still use it. Teardown that may block runs on a retained non-daemon cleanup thread; lifecycle calls use one overall monotonic deadline for serialization and joins, bounded to at most 30 seconds. A zero-second call requests the fence without claiming closure. Calls from the service/teardown thread refuse a self-join.

Repeated successful stop/close calls are idempotent. Timeout returns a typed receipt with `timed_out=True`, preserves the live thread and open resources, and allows the owner to call close again. A callback ignoring cancellation, partial wire request, slow close or blocked OS operation can outlive the caller's wait; no Python wrapper can safely kill such a thread. The handle must remain owned and reachable. The owner must retain the attempt/reservation and reconcile the underlying operation; never close its raw SQLite handle to force progress. The currently synchronous server bounds a partial initial frame with its existing receive deadline. The wrapper does not replace or widen that protocol deadline.

`WorkerServiceReceipt` is frozen and contains `service_id`, the captured immutable `AttemptBinding`, `started`, `stop_requested`, `thread_stopped`, `active_callbacks`, `listener_closed`, `resources_closed`, `timed_out`, and a fixed sanitized `error`. `receipt` computes a fresh observation; it is not a stale cached success. `thread_stopped` covers the service and retained teardown thread, including an unstarted service. `closed_receipt()` refuses unless the stop fence is set, all owned threads have stopped, callbacks are zero, and listener plus resources are closed. Historical fixed service errors remain visible even if physical resource closure later succeeds. Closure errors can be retried; an uncertain error never sets the corresponding closed flag.

The controller must bind the receipt to the exact service object and `service_id` plus attempt/generation/profile binding. The read-only `dispatcher` property exposes the original exact `WorkerDispatcher` so the controller can additionally require its `execute_request` to be the expected `SupervisedProviderExecutor`. The server uses a guarded proxy that tracks the complete dispatch call, including its final journal write, and rejects overlap or post-stop admission. Closing through that proxy is refused. The trusted owner can still misuse the original dispatcher returned for identity checks; direct mutation or closure violates the exclusive-ownership contract.

Service closure is a socket/thread/journal fact, **not provider container cleanup**, caller cleanup, credential-reuse authority, budget release, successful delivery or workflow acceptance. The controller still needs exact supervised executor/provider cleanup receipts and the scheduler's existing release gates. A response may have completed before a concurrent stop request; stopping cannot retroactively retract already written bytes. During active dispatch, the existing cancellation event causes `WorkerDispatcher` to replace a would-be success with its cancellation response.

The tests use actual local Unix sockets and real dispatcher journals with synthetic callbacks. They cover successful response and ordered closure, active cancellation, a callback that delays draining, incomplete framing, unstarted/dead service handling, concurrent closes, fixed failure receipts and retries, slow resource closure, self-join refusal, post-stop dispatch fences, socket replacement preservation and exact receipt identity. No provider request, remote host operation, live service or production integration is performed by this module checkpoint.
