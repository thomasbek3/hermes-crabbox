# D9 durable dispatch foundation

This local module separates the persistent logical provider account owner from each disposable request's provider container, gateway container, internal network and external network. It has no listener, Docker adapter, provider invocation, token access or deployment integration. Internal IDs are not bearer credentials. Only the existing trusted worker may compose this API with authenticated role routing and credential provisioning.

`ProviderLeases.reserve(account_id, persistent_owner_id=...)` reserves the account in the same SQLite transaction domain as legacy `Store.claim_next()`. `ProviderDispatch.admit` receives that reservation and a distinct controller execution grant, a 64-hex request nonce (the original relay nonce, never truncated), bounded transcript bytes and a 64-hex immutable profile digest. It stores the payload digest, profile digest, grant, attempt/generation, launch nonce and exact resource names. Same nonce and same immutable inputs returns the original dispatch; conflicting payload/profile/reservation refuses. A new nonce cannot change the attempt-generation profile. Thirty-two new requests per attempt is the implemented cap; retries of the same admitted nonce do not consume it.

The account OS flock covers admission and the complete create/bind/start seam, collection and cleanup. Lock acquisition waits at most five seconds by default; account_lock_busy leaves state unchanged. A cancellation supervisor must retry cleanup lock acquisition without replaying inference. Its private directory accepts owner-only0700 or2700; files require owner600, one link, no symlink. Locks are per-account SHA256 names and process-instance scoped. The actual subprocess-death test proves kernel flock release while the SQLite create intent and account ownership remain held. A new controller cannot adopt the prior controller instance merely because its PID is gone.

## Runtime interface

The injected trusted runtime supplies:

- `create(spec, payload, deadline=...) -> Resources`: create, but do not start, both containers and networks. No provider or gateway execution during create. Return all four distinct full64hex IDs.
- `inspect(spec, resources, deadline=...) -> tuple[ObservedResource, ...]`: independently inspect provider, gateway, internal network and external network in that order. The module checks exact full IDs, deterministic names, labels and observed states. Network presence uses `state='created'`; network mode, endpoints and absence of other peers must additionally be verified by the eventual adapter. Container-only inspection is insufficient.
- `start(spec, resources, deadline=...)`: start only the bound IDs after the second authorization check. The adapter must not accept arbitrary caller names, URLs or configuration. It must bound every operation and ensure cancellation can fence any late completion.
- `collect(spec, resources, limit=..., deadline=...) -> bytes`: a bounded response; the default module limit is256KiB. Store the response and its SHA256 durably before cleanup.
- `resolve(spec, frozen_row, deadline=...) -> OperationResolution`: independently reconcile an unknown external operation using definitive completion/no-effect/fencing evidence. Return exact request, launch nonce, operation, frozen version, resource IDs and evidence hash. A missing object, timeout, Boolean or invented hash is insufficient. This callback is trusted code, never model input.

Resources have exact per-launch names `cwb2-e<EPOCH>-<LAUNCH>-provider`, `-gateway`, `-internal`, `-external`. Labels bind reservation, epoch, request and launch; container component is provider/gateway. Networks carry gateway component plus internal/external network role. The old generic runtime create helper starts its gateway early and cannot be reused unchanged.

The mandatory lease cleanup verifier receives all four names/IDs plus the immutable launch/payload/profile/attempt/generation and dispatch version. It must stop/remove or definitively fence the whole scope, including late create/start and credential writers, and produce a typed receipt. It runs outside the SQLite write transaction but under the account flock. A second transaction verifies unchanged identity before releasing the request. Logical account ownership remains held. Owner cleanup requires the wider all-request proof. No request can reassign the credential based solely on process-group cleanup.

## Durable state and failures

The implemented states are admitted, create_intent, created, start_intent, running, collected, cleaning, cleaned, delivered and quarantined. Failed is reserved. Create/start intent commits before external work. Unknown external outcome quarantines and retains the account/request, even when subsequent inspection returns no objects. Resolution never restarts or automatically retries a prompt. It only permits a later independently verified cleanup. A stored definitive resolution is included in the cleanup target. Cleanup commits its own uncertain cleanup intent before invoking the verifier, so process death during cleanup also requires reconciliation. Verifier errors become unknown operations and cannot be retried as absence-only success. Pre-verifier owner/lease refusals leave the dispatch unchanged and do not invent an external operation. Known no-resource cleanup accepts an exact trusted definitive receipt with no IDs; once IDs are bound, every start/cleanup resolution must retain all four IDs even when resources have been removed. Failed resolution increments its CAS fencing version while preserving the original failure code.

Store cancellation, fencing and terminal transitions revoke grants and mark dispatch cancellation in the same database transaction. Cancellation between create and start prevents start. Cancellation during start makes cleanup contend for the same flock and prevents response delivery; a busy-lock timeout requires a later cleanup attempt. Cached response retrieval rechecks attempt generation, owner revocation and grant. `deliver` means returning bytes to the trusted relay caller after durable cleanup, not proof that an HTTP client received them. Same-nonce response caching is allowed; HTTP delivery ambiguity must interrupt the attempt at the integration layer and must never become a fresh model prompt retry.

Observed grant/request expiry remains durable across clock rollback. Expiry denies access; it never auto-releases ownership. Grant and attempt checks repeat around collection. Callback exceptions are reduced to safe fixed codes. An unknown inspector operation remains held until reconciliation. The injected callbacks must enforce supplied deadlines internally: post-call deadline checking cannot interrupt a hung Python callback. There is no unbounded background thread workaround.

## Evidence and remaining activation gates

`tests/test_provider_dispatch.py` uses synthetic runtime objects and real local child processes killed during create and cleanup intents, then drives a new controller through definitive reconciliation, owner release and a new account epoch. These prove controller sequencing and lock recovery, not Docker, credentials or provider behavior. Existing lease/Store/runner tests preserve admission races, raw old-writer SQL fences, cancellation and recovery behavior. Experimental pre-D9 or partial provider schemas are explicitly refused; this is not a live database migration. No live database was opened or changed.

Before activation, qualify the actual Docker adapter's internal isolated networking, all four resource inspection/cleanup, bounded commands and late-operation reconciliation. Integrate attempt-scoped UDS/HTTP relay authentication, native SDK retry suppression, periodic250ms cancellation observation, abrupt UDS disconnect, outer HTTP delivery-unknown handling, readiness and actual provider protocol/auth. Root-wide128 requests,60/min burst4, frozen root ancestry and resource arithmetic require the parent controller policy integration; this foundation does not infer ancestry from legacy fields. Admission persists the earlier caller root deadline or grant expiry and reserves40 seconds after the request execution deadline. The120-second execution maximum is clamped to elapsed durable request expiry and passed through create/start; the160-second minimum remaining admission reserve is enforced from the trusted caller value. A real adapter must clamp actual execution plus cleanup against the root wall-clock and persist any remaining timing metadata needed after crash. The existing approved provider bootstrap is an upcoming composition boundary, not used by these tests.
