# Infrastructure reuse assessment — 2026-09-18

Research only, requested after Thomas paused the build. No installations, service changes, migration, provider calls, tests or checkpoint-review runs were performed for this assessment. The build goal stays paused. This document proposes choices; it does not replace the approved specification or authorize cutover.

Recommendation: Coder is the stronger candidate for replacing substantial workspace infrastructure while retaining Hermes. OpenHands Sandbox Server is usable infrastructure, but its complete task/conversation experience assumes the OpenHands SDK. Do not adopt both by default. For only a headless task on one Docker host, the already-working Hermes execution plus a small dispatch/result adapter may remain simpler than introducing either platform.

The requested outcome is MUSE/Grokbot submits a task → a fresh Hermes worker performs it → results persist → compute is removed. Only an explicit same-task follow-up can restore task-specific state. Generated skills, memory and configuration must not propagate into unrelated workers.

| Responsibility | Coder | OpenHands Sandbox Server | What remains ours |
|---|---|---|---|
| Provision environments | Terraform templates for Docker, VM or Kubernetes resources | Docker/process/remote sandbox service abstractions | Select template/image and task-specific policy |
| Lifecycle | Workspace creation and start/stop/delete build transitions | Sandbox start/pause/resume/delete APIs | Task-to-runtime ownership, completion and cleanup ordering |
| Remote work access | Workspace connectivity, SSH, terminal and optional IDE/apps | Agent-server command/file interfaces and exposed sandbox endpoints | Hermes integration and task output capture |
| Agent loop | External Hermes can run in a workspace; native Coder Agents is optional and different | Stock conversation creation uses OpenHands Agent/LLM types | Keep Hermes and approved pstack model routing |
| Durable task results | Workspace storage can persist, but workspace deletion can destroy it | Conversation exports/archive behavior belongs to its own application/backend paths | Preserve our external result store and task manifest before deletion |
| Clean unrelated tasks | Per-workspace resources can be templated | Per-sandbox images/resources can be provisioned | Fresh Hermes home, curated base skills, no personal-state import |
| Credentials | Workspace secret injection is available, but injected secrets exist there | Sandbox-scoped secret retrieval exists | Provider auth ownership and separation from model-controlled shell |

Coder can replace or reduce our custom environment provisioning, workspace lifecycle, connection/access surface, and portions of terminal/app exposure. It does not replace provider login/refresh, Hermes JSONL handling, pstack/Jev routing, same-task continuation, or immutable result publication. Existing modules such as environments.py/runtime.py/preview_gateway.py/dashboard.py contain responsibilities that overlap; that is a replacement candidate map, not permission to delete those files.

Coder's API creates workspaces and its build API drives lifecycle transitions. The documented CLI can run commands through workspace SSH. Build and workspace-agent logs are infrastructure/process logs; capturing a Hermes transcript and associating it with a task is still an adapter concern. Sources: [workspace API](https://coder.com/docs/reference/api/workspaces), [build API](https://coder.com/docs/reference/api/builds), [SSH](https://coder.com/docs/reference/cli/ssh), [agent API](https://coder.com/docs/reference/api/agents).

For Omarchy, a Docker template is the relevant starting point. Kubernetes or a VM provider is optional additional infrastructure, not a prerequisite for retaining Hermes. Coder adds a control service, a database and Terraform provisioning. Its own native AI agent loop is distinct from hosting Hermes; the workspace connection daemon is not another LLM. Sources: [Coder architecture and external agents](https://github.com/coder/coder), [Docker deployment](https://coder.com/docs/install/docker), [Docker template](https://github.com/coder/coder/blob/main/examples/templates/docker/main.tf).

Coder persistence must be deliberate. Stopping can remove compute while retaining task-specific storage; deleting the workspace can destroy its managed volume. Its Docker example names the home volume by workspace UUID. Our design must export final results first and either discard the task profile or retain it under the original task ID for explicit continuation. A stopped reusable workspace is not equivalent to a clean unrelated worker. Source: [resource persistence](https://coder.com/docs/admin/templates/extending-templates/resource-persistence).

Community workspace capabilities should be evaluated separately from premium governance and the native AI product's licensing. Do not assume an AI Gateway entitlement or native-agent concurrency allowance applies to external Hermes workers. Sources: [plans](https://coder.com/pricing), [native-agent licensing](https://coder.com/docs/ai-coder/agents/licensing-usage). No paid feature or spending was selected here.

OpenHands Sandbox Server is a standalone API/control-plane extraction, separate from Agent Canvas. It explicitly depends on openhands-agent-server, openhands-sdk and openhands-tools. Its conversation layer imports OpenHands Agent/LLM/context types and loads skills from user, project, organization and marketplace sources. Therefore its whole conversation API is not a drop-in Hermes task API. Sources: [repository](https://github.com/OpenHands/sandbox-server), [dependencies](https://github.com/OpenHands/sandbox-server/blob/main/pyproject.toml), [conversation implementation](https://github.com/OpenHands/sandbox-server/blob/main/openhands/app_server/app_conversation/app_conversation_service_base.py).

Lower-level reuse is plausible: create a sandbox, use the agent-server HTTP command/upload/download interface as a Hermes tool backend, and retain Hermes outside it. Those operations do not require adopting the OpenHands reasoning loop. That still needs an adapter for execution, timeouts/cancellation, files and result mapping; no compatible adapter was established in this research. Sources: [agent-server operations](https://docs.openhands.dev/sdk/guides/agent-server/overview), [remote workspace implementation](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/workspace/remote/async_remote_workspace.py).

OpenHands' Docker service is not our desired isolation policy out of the box: the inspected creation path uses configured mounts and bridge/optional host networking; it does not set our CPU/memory/PID limits in that call. Its default extra-host mapping permits reaching the host gateway. Sandbox deletion is also separate from conversation workspace archival, and archival is not implemented identically by every backend. This is integration work, not a blanket security assessment. Source pinned during the read: [Docker service](https://github.com/OpenHands/sandbox-server/blob/f19f9e0d88272bb393e39e8cbcb78e3e8aa633a3/openhands/app_server/sandbox/docker_sandbox_service.py), [sandbox service archive contract](https://github.com/OpenHands/sandbox-server/blob/f19f9e0d88272bb393e39e8cbcb78e3e8aa633a3/openhands/app_server/sandbox/sandbox_service.py).

The preferred proposed topology keeps one fresh Hermes worker and a separate command sandbox. The task bridge asks Coder to create the command workspace, starts Hermes with a new task-specific profile, connects its tools to that workspace, captures outputs in persistent task storage, and tears down compute. There is only one Hermes reasoning agent in this design. A simpler alternative runs Hermes directly inside the Coder workspace, but that does not provide the same separation between provider credentials and arbitrary shell commands. Neither topology was installed or exercised.

Hermes already has an SSH execution backend, making Coder connectivity promising. Current upstream also synchronizes selected credentials, skills and cache and syncs changes back. Consequently SSH alone is not a guarantee of clean tasks or credential exclusion: use a dedicated task home and explicit allowed content, never a personal ~/.hermes. This is a source-level integration lead, not a compatibility claim for our pinned deployed image. Sources: [Hermes SSH backend](https://github.com/NousResearch/hermes-agent/blob/main/tools/environments/ssh.py), [file synchronization](https://github.com/NousResearch/hermes-agent/blob/main/tools/environments/file_sync.py).

Keep custom scope small: submission/status/cancel/result calls for MUSE/Grokbot; task identity and optional continuation; the Hermes process adapter; credential boundaries; artifact publication and cleanup ordering. Prefer upstream workspace management to expanding a second general-purpose control plane. Preserve all current work and existing jobs until Thomas selects a direction and explicitly resumes implementation.
