# Remaining worker integration for routed stages

The driver, provisioning primitive, bounded worker lifecycle and combined cleanup components now exist. They remain an undeployed candidate; a complete production orchestration entry point and protected result path are still required.

1. Use `plan_child_stage` to derive the exact admitted profile, instructions, revision and launch. Invoke `RoutedBootstrap.provision` through a root-owned authorization boundary, then call `prepare_child_stage(..., expected_plan=planned, required_tool_gid=1000)` into the returned materialization parent. The root authorization/IPC adapter is still missing. The helper itself is implemented and the actual UID959/GID960 with supplementary959/966 permission proof passed on Omarchy without group changes. See ROUTED-BOOTSTRAP.md. The worker's controller journal/runtime directories must remain private0700 and outside caller mounts.
2. Compose `AttemptBinding`, `ProviderExecutor`, `SupervisedProviderExecutor`, and `WorkerDispatcher(execute_request=wrapper, authorize=wrapper.authorize)`. Wire the provider adapter's cancellation callback to `wrapper.cancel_check`. Snapshot and dispatch must share the same leases object. The provider runtime must expose the exact material-cleanup hook; account credentials remain outside the caller.
3. Wrap the exact `WorkerSocketServer` in `WorkerService`, retain the handle, and start it before `drive_prepared_child`. Shutdown closes admission, signals callbacks and joins the synchronous handler before closing its journal. Timeout retains handles and prevents cleanup success. The actual Linux UDS fixture proved these interfaces under worker959; it did not run a provider container or full driver.
4. Run `drive_prepared_child` with the provisioned CallerSpec and fresh scheduler authority. It binds before start, checks relay readiness and authority, collects worker-reported observations, fences grants, and removes only the exact caller. Preserve its QuiescedStage and every worker service handle. Its result cannot pass verification or release capacity.
5. `RoutedChildCleanup` now aggregates fresh exact caller removal, worker/executor/supervisor shutdown, every child grant/request and physical plus private material cleanup. It reconciles unknown provider operations only through definitive runtime evidence, replays material cleanup for already-cleaned requests and retains root account reservations. It saves a bounded durable combined receipt. Its verifier can later support `scheduler.release_child` once a protected terminal decision exists. A stuck observer quarantines and retains ownership; automatic recovery of that condition remains unqualified. See ROUTED-CHILD-CLEANUP.md.
6. `save_observation` now persists validated raw bytes before driver teardown; `load_observation` restores them under the same current controller authority. `publish_observation` implements immutable artifact publication with final transactional authority, budget and exact combined-cleanup checks. Wire these components into the root entry point, passing the explicit controller-known-secret policy to driver and result composition. The pre-snapshot raw/decoded-value check is now implemented; no credential discovery is performed by these APIs. Fresh-controller takeover remains separate; the snapshot alone cannot authorize adoption or publication. See ROUTED-OBSERVATION-STORE.md and ROUTED-PUBLICATION.md.
7. `export_stopped_workspace` implements the exact-mounted, read-only, networkless UID1000 collector with bounded descriptor-validated output and a private durable spool. `load_workspace_export` restores the completed export without another launch. `capture_exported_candidate` binds the original workspace identity, rechecks authority/cleanup and registers an immutable unverified revision. Local coverage and actual Linux UID959/UID1000 export plus durable reload now pass (`evidence/routed-export-linux-20260918-v3.json`). The exporter now attempts bounded exact cleanup automatically after failure and records aborted/recoverable/ready status. `publish_child_results` reconciles any prior export before cancellation-sensitive publication; genuinely running timeout and cancelled-retry tests pass. Preserve uncertain journals and ownership. Production startup must still reconstruct the exact handles and invoke reconciliation; unresolved create/absence is never reset or interpreted as success. Then wire protected checks, output/gate/promotion decisions and child release. See ROUTED-EXPORT.md and ROUTED-CANDIDATE.md.
8. `publish_child_results` composes the result phase; connect it and the preceding launch components into one reviewed worker entry point, qualify the exact real providers and full six-stage coding job, and prepare migration/activation without restarting legacy cloudd or discarding current jobs. Existing isolated receipts do not establish production activation.
