# Produced workspace candidates

`capture_exported_candidate` composes the stopped-workspace export with existing immutable `WorkspaceRevision` capture. The trusted controller passes its original `PreparedStage`, exact `CallerSpec` and `QuiescedStage`, the live `RoutedChildCleanup` handle, and a `WorkspaceExport` whose collector has already been removed. The original materialization's device/inode must match the exported workspace. The private export journal binds the returned file bytes and original caller identity; constructing a dataclass is insufficient.

The function rechecks current scheduler ownership, root/child/session/turn generations, launch binding, assignment, cancellation, client scope and budget. It replays combined cleanup and validates its durable evidence, then copies the bounded decoded tree into fresh staging inside the controller's private runtime directory. Existing revision capture validates explicit selectors and known-secret exclusions and publishes the immutable candidate in a separate controller-private revision directory. Staging is removed after the copy; it is never mounted into a caller.

A final bounded SQLite transaction repeats authority and cleanup membership checks, registers the manifest artifact, records `workflow.candidate_published`, and advances the budget observation high-water mark. Exact replay is idempotent; changed metadata or incomplete event registration refuses. Cancellation after immutable capture can leave an unregistered revision for retention/reconciliation, but cannot register or advance it. An event failure rolls back artifact registration; retry uses the original completed export rather than launching another collector or provider request.

The returned candidate binds input and output revision hashes, export and cleanup evidence. Its verification flag is always false. No child state, workflow gate, shared account reservation, scheduler seat or delivered session pointer changes. A reviewer can materialize the immutable candidate read-only using the existing revision interface. Protected verifier execution, outcome decisions, next-step admission and final session promotion remain separate integration work.

The artifact is the candidate manifest; API access requires the configured artifact root to contain the revision directory. Individual file delivery and complete root bundles still require result integration. This module does not claim deployment or a full successful cloud job.
