# Routed workspace revision primitive

`cloudworkbench.workflow_revisions` captures selected deliverables from a quiesced routed workspace into controller-owned, hash-bound storage and creates isolated stage copies. It uses the existing Store session/attempt identities. It adds no database, scheduler, lifecycle state, canonical-session pointer, or delivery-success decision. Existing direct Claude work/native layouts and Runtime launch behavior are unchanged.

## Controller integration

1. Construct `RevisionBinding(owner_id, project_id, session_id, turn_id, root_attempt_id, root_generation, attempt_id, generation)` from trusted Store rows, never model-supplied scope. `validate_binding` checks schema 2, Hermes root/child identity, the exact root generation, owner/project/session/turn, and child parent/generation correlation. This is identity validation, not an authorization, cancellation, reservation, or lifecycle check. Capture may retain a stopped failed candidate as evidence; it does not require a successful attempt.
2. Stop/quiesce every writer and establish that fact with the existing runtime cleanup/writer-reservation mechanism. Then call `capture_revision(store, binding, workspace, revision_root, selected_paths=('src', 'README.md', '.github'), controller_attests_quiesced=True, forbidden_values=(...))`. The boolean is the trusted controller's attestation; the primitive does not inspect Docker or prove physical quiescence. `workspace` must be the approved deliverable work tree, not a session directory containing native state or a home directory. The source/storage paths and selection policy are trusted controller configuration, not broker/model input.
3. `revision_root` must already exist in controller-owned storage outside the workspace, with no job write access to it or its ancestors. The result is `WorkspaceRevision(path, sha256, binding)` under `revision_root/<sha256>`, containing `manifest.json` and `files/`. Persist the exact hash/path/binding through the existing controller artifact/result metadata path and use the same hash for scheduler `input_revision_sha256`/gate evidence. The primitive does not register an artifact or promote a delivered revision itself. Existing immutable artifact download APIs must not serve the worker's original writable tree.
4. Call `materialize_stage(store, revision, consumer_binding, fresh_destination, readonly=True, required_tool_gid=1000, before_publish=guard)` for the current numeric review/coordinator caller, or `readonly=False` for a coding/synthesis stage. Consumers must have the same owner/project/session/turn/root ID and root generation; attempt identity may differ. Each call verifies every stored file and creates a separate source copy and empty scratch directory. Existing destinations are refused. The optional trusted `guard(consumer_binding)` runs after copying and immediately before publication; only literal `True` permits publication. Rejection or an exception removes the unpublished private staging copy. It must recheck full stage authority, not only identity. The group and guard defaults remain optional for standalone filesystem use; a production driver must supply its required contract. There is no cross-root follow-up/import API here; a future controller-authorized follow-up must explicitly rebind a verified delivered revision rather than bypass this check.
5. The returned `StageMaterialization` contains `source`, `scratch`, `revision_sha256`, `consumer`, `readonly`, and `mounts`. Its concrete contract is `{source: source, target: '/workspace', readonly: True}` for a reviewer and `{source: scratch, target: '/scratch', readonly: False}` for scratch. A coding copy uses `readonly: False` for its own `/workspace`. Mount only those exact subdirectories, not their parent, original workspace, storage root, another stage, or native/auth state. The existing generic Runtime protects `/workspace`; this return value is a contract for the routed caller driver, not an instruction to bypass Runtime's validation.
6. Before launch, the driver must atomically recheck current generations/cancellation/owner authority and reserve the stage through the existing scheduler. File publication and DB admission are not one transaction. Generation checks immediately before publication reject observed drift, but do not close the interval before launch. The driver must enforce and inspect Docker read-only bind flags, resource/egress limits, and separate scratch. File modes alone are not read-only container isolation. A coding result becomes a new candidate only after its writers stop; required review and protected verification must reference that exact hash before a separate CAS promotion.

The controller must provision the destination parent's ownership and setgid group to match its configured caller tool group. `required_tool_gid` checks that the immediate parent is setgid with that GID before copying, and verifies the inherited group on every staged entry before publication. The module does not chown or create host users. Stored/read-only files are 0440, executables/directories 0550; writable stage files are 0660, executables/directories 0770, scratch is explicitly chmod0770 regardless of umask, and its controller metadata parent is 0750. These modes are storage hygiene and a group access contract. Actual numeric-UID readability and read-only mount enforcement still need runtime qualification.

For worker UID959 and caller1000:1000, the existing root-installed `workspace-volume` helper can provision a **new attempt-scoped bounded volume** whose `work` directory is959:1000 mode2770. The worker can create owned files there with group1000 inherited, without gaining arbitrary chown authority. Do not change an existing session volume's receipt/identity or use caller-readable groups for canonical controller revision storage. This is a provisioning proposal, not an executed host change. Reverse access also needs qualification: files newly created by caller UID1000 may be unreadable by worker959, especially mode0600. Shared group membership alone does not fix0600. The deployment must supply a narrow output-access/collection contract and test new-file→stop→controller capture. Neither group inheritance nor this module claims that capability is already proven. Init UID1002 and relay UID1001 should use a neutral container working directory rather than requiring traversal of the group1000 workspace.

After a returned materialization, the stage preparer must still perform its final authority check. If that fails **before any runtime create/start**, it may call `discard_unlaunched_materialization(value, controller_attests_unlaunched=True, limits=...)`. This accepts the exact returned handle, never a standalone destination path. The handle binds a fresh publication nonce, stage/source/scratch device+inode identities, metadata digest, source-tree digest and consumer/revision. Discard checks all those bindings, an unchanged source tree and empty scratch, then removes only that tree with descriptor-relative, no-follow operations under the trusted parent's publication lock. Foreign replacements, tampered metadata, added root entries, modified source or scratch evidence are retained with an error for explicit recovery. The original immutable revision and sibling stages are untouched. The controller's no-runtime attestation is essential: filesystem checks cannot prove the directory was never mounted. Never use this helper for a running, previously mounted or uncertain-launch stage. A crash before a handle is returned or an uncertain cleanup still requires identity-bound reconciliation rather than generic path deletion.

## Selection, integrity and limits

Selections are an explicit nonempty tuple of relative file/directory paths. Whole-tree `.` selection, overlapping roots, traversal, backslashes, control characters and oversized names are refused. `.github`, `.gitignore`, and ordinary hidden deliverables are supported. Specific private/dependency state is refused anywhere in a selected subtree: `.git`, `.hermes`, `.codex`, `.claude`, `.ssh`, `.aws`, `.azure`, `.config`, `.local`, `.cache`, `.credentials`, `credential_state`, `credentials`, `auth`, `native`, `.npmrc`, `.pypirc`, `.netrc`, `.docker`, `.kube`, `.gnupg`, `.envrc`, `.env`/`.env.*`, `auth.json`, `credentials.json`, `token.json`, `tokens.json`, `node_modules`, `.venv`, and `__pycache__`. Unselected paths are never traversed. This is a selected-deliverables manifest, not a complete workspace dump. Names cannot detect arbitrary embedded credentials or transcripts: trusted selection and the controller's known-secret byte scan remain required boundaries.

Reads open each directory component relative to descriptors with no-follow semantics. Symlinks, hardlinks, devices, sockets and FIFOs are rejected. File and traversed-directory identities/timestamps are rechecked after reads; observed mutation aborts the whole capture. Files are copied from those exact bounded bytes, hashed, flushed, and staged before publication. Defaults are 32 MiB, 2,000 entries, depth 32, and a 30-second scan budget; explicit configuration is capped at 128 MiB/10,000 entries/depth 64/120 seconds. Manifests are capped at 2 MiB. Time checks bound cooperative scanning; they do not interrupt a blocked kernel/filesystem operation or impose a hard deadline on fsync.

The canonical manifest binds the producer identity, selected roots, directory set, file paths/lengths/SHA256/executable bits, and selected scope. Its digest is the revision ID; identical bytes from another producer/root are a distinct revision. Verification rehashes all files and refuses unexpected entries, missing/changed content, unsafe paths, or a changed manifest. It does not merely trust chmod or timestamps. Cooperating publishers take a nonblocking advisory lock on the trusted parent directory and publish by rename; conflicts fail closed. Other controller processes must not mutate or replace storage behind this boundary. An interrupted post-rename fsync can leave an unregistered candidate; a repeated capture verifies an existing hash before returning it. Materialization is fresh-only and leaves registration/recovery to the driver.

## Local evidence and limits

`tests/test_workflow_revisions.py` covers actual Store/schema-2 identity binding, child materialization, cross-root refusal, selected-only copying, valid dotfiles, executable bits, source mutation and directory replacement, stale-generation refusal before publication, corruption/extra-file detection, symlink/hardlink/FIFO rejection, byte/entry bounds, secret rejection, conflict preservation, isolated coding edits and scratch, and legacy-schema refusal. Corrective tests additionally cover setgid parent requirements, inherited-group mismatch, restrictive-umask scratch creation, rejected/raising prepublication authority checks, exact unlaunched discard, and foreign replacement/changed-work refusal. These are local synthetic filesystem/identity tests. They do not prove Docker mount flags, numeric tool UID access, disk quotas, live writer quiescence, provider execution, workflow completion, artifact registration, or delivery promotion.
