# Retention controls and dry-run inventory

The default session deadline is **30 days after last activity**. `keep` defaults false and prevents eligibility regardless of the deadline. Last activity is the latest session creation, turn, attempt creation/update, event, or retention-control change. Downloads and read-only inspection do not extend it. Archive is an explicit state-changing user action and emits an activity event, so it extends the rolling deadline; it still neither expires nor purges data. An explicit timezone-aware `deadline` can override the rolling deadline; setting it back to null restores rolling behavior. Explicit deadlines must be within 3650 days of the control update. If a native interval is configured, its deadline must precede the explicit session deadline; later activity that reverses that order protects the session pending policy review. Expiry only changes a computed review status: it does not modify attempt states, archive, cancel or purge anything.

There is **no deletion executor, scheduled cleanup or adopted deletion policy**. `DELETE /v1/sessions/{id}` still returns 501. This unit does not run filesystem scans, revoke credentials or stop processes.

## API and integration

- `GET /v1/sessions/{id}/retention` and `GET /v1/sessions/{id}/retention/dry-run` return the same bounded plan. Both require `observe`, owner identity and the session's project allowlist.
- `PATCH /v1/sessions/{id}/retention` requires `submit`, the same ownership/project check, and `Idempotency-Key`. Body fields are `expected_revision` plus one or more of `keep`, `retention_days`, `deadline`, `native_hours`, `secret_hours`. Unknown fields and coercions such as `keep: 1` are rejected. A stale revision returns 409; replay of a successful request with the same idempotency key returns the original response. Failed transactions leave no idempotency record, so a corrected retry can use the same key.

Example body to retain a session: `{"expected_revision":0,"keep":true}`. An explicit deadline body is `{"expected_revision":1,"deadline":"2026-12-01T00:00:00Z"}`. These are control requests, not deletion authorization.

The additive `session_retention` table stores only policy JSON, revision and update time. Existing sessions inherit defaults without per-session writes. The existing Store creates this table and wraps control changes in its write transaction/idempotency/event machinery. Using the existing `submit` scope for reversible policy controls is deliberate: it matches archive/follow-up ownership, adds no administer/purge permission, and cannot execute deletion. The pure `retention.py` functions accept caller-owned SQLite connections: callers must authorize first, supply a consistent read transaction for plans, and a serialized write transaction for changes. Missing additive policy keys inherit current defaults on read; incompatible values or unknown keys still fail closed and require an explicit migration. No automatic backfill touches old jobs.

## Manifest protections and limits

Queued, live, unknown and paused checkpoint attempt states protect the session regardless of age; `keep` does likewise. Protected sessions return an empty `deletion_manifest` while retaining a read-only logical inventory explaining their protected status. Although the runtime lifecycle classifies paused as terminal (no live runtime), retention conservatively protects its durable continuation checkpoint. Other closed states do not prove actual runtime quiescence; a future executor must independently establish it.

Plans are limited to 10,000 logical items and 1 MiB serialized output by default; overflow fails closed with 413 instead of issuing a partial manifest. Plans contain artifact IDs, safe relative names, database SHA256/byte identities, attempt result/log identities, workspace identity and repository baseline identity. Controller storage paths and credential identities are not exposed. Filesystem sizes and identities not yet scanned are explicitly unknown. The snapshot SHA256 binds session/policy revision, attempt states and generations, event sequence, activity and artifact metadata. `require_matching_plan` rejects changed snapshots; a matching hash is never authority to delete and never substitutes for actual nofollow filesystem hash/inode checks.

Shared supplied inputs remain excluded because other sessions/future turns may reference them. Native conversation state is separately identified, marked sensitive and excluded from the session deletion manifest. Provider credential/cookie roots are never walked or included.

`native_hours` and `secret_hours` default **null / no policy**. The specification supplies no numeric defaults for those categories. Explicit configured values must be positive and shorter than session retention, with secret lifetime shorter than native lifetime when both are set. Their fields provide independent policy review controls only; no secret is inventoried, no secret deadline is inferred from session activity, and no secret cleanup is marked adopted. `keep` also protects native-state review eligibility. No secret deletion authority is inferred from `keep` or session expiry. Artifact metadata with native, credential or shared-input path components is refused without echoing the path.

Before any future purge executor or schedule: adopt the policy explicitly; obtain scoped purge authority; regenerate and compare the database snapshot and policy revision; prove runtime/filesystem quiescence; inspect bounded nofollow inode/content identities and shared references; separately resolve native/secret ownership and retention; record a durable tombstone. These are future executor gates, not operations performed by this module.

## Validation

Focused tests cover exact rolling deadline boundaries, configured deadline/keep, CAS and idempotency, resumed activity, archive separation, queued/live/unknown-state protection, owner/project/scope isolation, malformed metadata/policies, bounded manifests, guarded artifact identities, separate native/secret treatment and unchanged disabled purge behavior. Fable returned REVISE; the separate disposition records verified corrections and the deliberate archive-activity policy instead of claiming a new Fable PASS.
